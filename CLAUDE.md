# Etsy Management System

This project is a local MCP-based system for managing Etsy shop(s) through Claude. The architecture supports multiple connected Etsy accounts; only one is connected today, but adding another is just running the OAuth helper again with a new name — no code changes needed.

## First run / broken setup — run `etsy-setup` first (explicit user instruction, 2026-10-07)

If any of these is true — no `.mcp.json` (Claude) or no Antigravity MCP config, `etsy-mcp-server/build/index.js` or `node_modules` missing, the `etsy` MCP tools are unavailable/failed to connect, or the project was just copied from another machine/OS — **do not start Etsy work.** Run the **`etsy-setup`** skill (`.claude/skills/etsy-setup/SKILL.md`): it asks **which OS (macOS / Windows / Linux) and which AI tool (Claude / Antigravity / both)**, runs `node scripts/setup.mjs`, verifies with `node scripts/setup.mjs --check`, and then guides connecting a shop and onboarding. Never ask the user to paste API secrets into chat — they go in `etsy-mcp-server/.env` (edited by the user, or typed into the setup script's own prompt in their terminal).

## Safety rule — ALWAYS CONFIRM BEFORE WRITE/DELETE

Any tool call that **creates, updates, or deletes** data on Etsy (listings, shop settings, sections, shipping profiles, orders, etc.) must be confirmed with the user **before** it is executed. Show what will change (which item, which fields, old → new values) and wait for an explicit "yes/haan/confirm" before calling the tool. This applies to every `create_*`, `update_*`, and `delete_*` tool below — never call them straight off a single ambiguous request. Read-only tools (`get_*`, `find_*`, `search_*`, `list_*`) do not need confirmation.

Reason: these actions are live and mostly irreversible against a real, active shop — an accidental delete or edit cannot be undone through the API.

## Standing rule — no digital/download listings on abbas_etsy (explicit user instruction, 2026-07-29)

`abbas_etsy` only sells physical products. Never create a digital/download listing (`type: "download"` or `"both"`, or any listing whose deliverable is a downloadable file — SVG/PNG/AI bundles, digital templates, etc.) on this account. This applies to every skill/flow that creates or clones listings (`etsy-create-listing`, `etsy-copy-listing`, `etsy-new-listing-copywriter`, `upload_listing_file`, or any ad-hoc draft) — if a request would result in a digital listing and the target account is `abbas_etsy`, stop and flag it to the user rather than proceeding (suggest `itrat_etsy` instead, since that's where this shop's whole SVG/digital line already lives — see `data/product-registry.json`). Physical listings for `abbas_etsy` are unaffected by this rule.

## Standing rule — show the full write payload as a table, not prose (explicit user instruction, 2026-07-23)

Whenever confirming a `create_*`/`update_*` call before executing it (per the safety rule above), present **every field being written** as a single markdown table, not a mix of headers, bullet lists, and blockquotes. This applies to `create_draft_listing`, `update_listing`, `update_listing_inventory`, `update_listing_personalization`, `upload_listing_image`/`upload_listing_video`, and every other confirmed write: title, tags, description, price, category, shipping, processing, return policy, personalization, materials, styles, variants, images — all of it goes in the table, not just the "easy" fields. This replaces the old habit of showing title/tags/description as headed prose blocks and the rest as a separate bullet table; going forward, everything about to be written is one table, shown before the write, every time.

- **Create calls** (nothing to compare against): two columns, `| Field | Value |`.
- **Update calls**: three columns, `| Field | Old Value | New Value |` — this is what actually satisfies the Safety rule's "old → new values" requirement above; a 2-column table on an update silently drops the old value the safety rule requires showing.
- **Multi-line fields in a cell** (a full description with paragraph breaks, a long tag list): join line breaks with `<br>` inside that cell so the table itself doesn't break — a raw blank line inside a markdown table cell splits the row. Variant matrices with more than ~10-15 rows may be summarized (e.g. "24 SKUs: 3 colors × 8 sizes, all $48.32, qty 50") rather than listed one row per SKU, to keep the table itself readable — call out any per-SKU value that actually differs instead of listing every identical row.

## Standing rule — when a live API call errors, fix it AND document it

Whenever a `create_*`/`update_*` call to the Etsy API fails with an error this project didn't already know about (a missing required field, a field-name mismatch, an unexpected format rule, an API limit) — don't just patch it in the moment for that one call and move on:

1. **Diagnose the real cause** — check the exact field/requirement via the `etsy-docs` MCP (`get_endpoint` for the operationId), don't guess from the error text alone.
2. **If it's a bug in this server's code** (`etsy-mcp-server/src/index.ts`) — fix it, rebuild (`npm run build`), and tell the user the running MCP server needs a session restart to pick up the new build (it won't reload itself mid-session).
3. **If it's a genuine Etsy API requirement a skill's field-gathering step didn't ask for** — update that skill's `SKILL.md` so the next run asks for/handles it upfront instead of discovering it live again. Name the **exact error message** the API returned next to the fix, not just a vague "handle this correctly" — that's what makes the note findable next time a similar error shows up. Keep `.claude/skills/<name>/SKILL.md` and `.agent/skills/<name>/SKILL.md` in sync (see "Deploying to Google Antigravity" below) — a fix in only one copy means the other AI tool hits the same error again.
4. **If it's project-wide knowledge** (not specific to one skill's flow, e.g. a generic-dispatcher fix or a field quirk that affects multiple tools) — add it to this file's "Which tool to call" section instead of a single skill.

The goal: this system gets more reliable with use — the same live-API error should never happen twice.

## Standing rule — the listings-record JSON is mandatory on every draft/publish/update

Any time a listing is **drafted** (`create_draft_listing`), **published** (`update_listing` setting `state: active`), or **updated** in any way (`update_listing`, `update_listing_inventory`, `upload_listing_image`/`upload_listing_video`, `update_listing_personalization`, etc.) — writing/syncing `data/listings/<account>/<listing_id>.json` is **not optional and not something to ask about**. It happens automatically, in the same turn as the confirmed Etsy write, no separate confirmation needed (it's local bookkeeping, not an Etsy write). Full schema and field-by-field detail: `.claude/skills/_shared/listings-record-guide.md`.

- **On create**: write the file immediately after `create_draft_listing` succeeds, before moving to the next step.
- **On any later update**: update the changed fields in that listing's existing record in the same turn as the Etsy write that changed them — never let the file go stale even for one response.
- **Capture everything**: every field that exists on the live listing belongs in the JSON — title, tags, description, price, quantity, who_made, when_made, taxonomy_id, materials, styles, shipping_profile_id, readiness_state_id, return_policy_id, processing_min/max, variants, images, video, and personalization (add a `personalization` object even though it isn't in the base schema template — the template is a floor, not a ceiling; nothing observed on the listing should be left out of the record because the schema doc didn't explicitly name it).
- **If a record is ever found missing** for a listing this system clearly built or touched (e.g. during an `etsy-listing-qa-check` run) — create it from the listing's current live state immediately, don't just flag it and move on.

This is easy to forget mid-flow when several other writes (shipping profile, personalization, images) are happening in the same conversation — treat it as part of *finishing* each write, not a separate later task.

## Standing rule — verify physical/construction claims against the actual photo before writing copy (explicit user instruction, 2026-07-23)

Before any title/tags/description text claims something about how the product actually looks or is built, **open the featured/thumbnail image (and any other product images in hand) with the Read tool and look at it** — don't take a supplier's spec-sheet text as ground truth for anything visually checkable. This is a standing habit for every listing this system creates or rewrites (`etsy-create-listing`, `etsy-copy-listing`, `etsy-optimize-listing`, `etsy-new-listing-copywriter`), not a one-off step.

Reason: a real listing (Pink Floral Camisole Top, itrat_etsy) was published claiming "zipper detail" straight from an AliExpress spec sheet's boilerplate text — the actual product photos clearly show a tie/bow halter closure, no zipper anywhere. Nobody looked at the image before writing that claim into the title, a tag, and the description; the shop owner caught it after the listing went live and it had to be corrected with a follow-up `update_listing`.

What to actually look for in the image (use judgment per product, but at minimum check the things a spec sheet is most likely to get generically wrong):
- **Closures/hardware** — zipper, buttons, ties/bows, laces, drawstring, velcro, hooks, or no closure at all. This is exactly what was wrong above.
- **Construction technique** — printed graphic vs. embroidered vs. sequined/beaded vs. woven-in pattern (these are different manufacturing methods and buyers search them as different terms).
- **Silhouette and fit** — oversized vs. fitted, cropped vs. regular/full length, sleeve or strap style, neckline/collar type.
- **Material/texture cues actually visible in the photo** — fleece vs. smooth vs. ribbed vs. sheer/mesh, even if the spec sheet names a specific fabric.
- **Color accuracy** — does the photo's actual color match the color name about to be used in the title/tags/variant list (don't blindly trust a supplier's color label like "khaki" or "beige" without a visual sanity check).
- **Any other specific feature the spec sheet claims** (pockets, hood, collar, strap count, pattern placement) — cross-check each claimed construction detail against the photo before it goes into copy, the same way the zipper claim should have been checked.

If a spec sheet's claim can't be confirmed or is contradicted by the photo, don't write it into the copy — describe only what's actually visible, or ask the user if it's unclear from the image alone.

## Standing rule — jewelry listings match the featured image to a saved aesthetic/style before writing copy (explicit user instruction, 2026-08-19)

For any jewelry listing — `etsy-create-listing`, `etsy-copy-listing`, `etsy-new-listing-copywriter`, `etsy-optimize-listing`, `etsy-seasonal-keywords`, or any ad-hoc jewelry listing/rewrite — before generating title/tags/description, **open the featured/thumbnail image with the Read tool and identify which of the saved aesthetic/style categories in `.claude/skills/_shared/etsy-aesthetic-styles-guide.md` (gothic, vintage/antique, celestial, minimalist, boho, dark academia, cottagecore, etc.) the actual piece in the photo matches** — not which styles the product category could theoretically support. This is an extension of the photo-verification rule immediately above (same "look at the actual image, don't trust the source text" discipline), applied specifically to style/aesthetic classification for jewelry, since that's what drives keyword choice on Etsy.

Reason: AliExpress supplier descriptions are written to rank broadly for *their* algorithm — stuffed with every style/keyword term that could plausibly apply to that general product type, regardless of what the specific piece actually looks like. This shop is listing one specific real product on Etsy, so the copy must target the vibe that piece actually has, not a generic keyword net copied from the source text.

**The workflow is a stop-and-report step, not a silent internal decision (sharpened 2026-08-19):**
0. **Entry point (explicit user instruction, 2026-08-19): the user hands over just the product's staging folder path plus its AliExpress source URL — Claude fills the `product-details.txt` BASIC INFO section itself**, not the user. From the folder's images and the source URL/page, determine and write in: the product's core/plain name, the category (matches the subfolder it's already sitting in, e.g. `Rings`), the AliExpress source URL itself, and physical-vs-digital. Create the file from `_template/product-details.txt` first if the product folder doesn't have one yet. Everything past BASIC INFO in that file (account, pricing, variations, shipping notes if non-default, personalization, materials, extra notes) is still the user's to fill in — this only moves BASIC INFO (and, per the steps below, STYLE MATCH) onto Claude, not the whole intake form.
1. Open the featured image and analyze it against the guide's categories. State the match to the user in plain terms before doing anything else — e.g. "this reads as Gothic + Vintage/Antique-inspired: [visual cues seen]." If it's a genuine toss-up between categories, or doesn't clearly match any of them, say so and ask the user rather than forcing a fit or silently picking one.
2. **Wait for the user to hand back real Etsy listing IDs/URLs** of competitor products in that same identified style — the user does this research step themselves once they know which style to search for; don't invent or guess at competitor listings yourself.
3. Pull those listings (`get_listings_by_ids` / `get_listing_details`) and use their actual titles/tags/descriptions as the grounded reference for this listing's copy — the same "never invented from general knowledge" discipline already used for `taxonomy_id` sourcing (see the `create_draft_listing` gotchas below), now applied to style/keyword research too.
3b. **Every time reference/competitor listings are pulled for a new listing — whether the user hands over the IDs or Claude finds them itself — report the average price across them and suggest a price for the new listing, every time, no exceptions (explicit user instruction, 2026-08-19).** Compute the average from each listing's real `price` (landed price — see the "Landed price, not bare price" rule in `etsy-seo-standards.md` if shipping cost varies meaningfully across the sample). State the average plainly, then **suggest pricing this listing below that average** — this shop's standing pricing strategy is to undercut the researched average, not match or exceed it — and give a specific suggested number, not just "price it lower." This applies beyond jewelry too: any time a skill or ad-hoc request pulls a set of reference/competitor listings to inform a new listing's price, the average + a below-average suggestion is a mandatory part of that report, not an optional add-on only given if asked.
4. Let the matched style(s) — pick the closest one or two, per the aesthetic-styles guide's own "pick two, not the whole list" rule — drive keyword/tag selection: prioritize language actually seen in those reference listings over generic jewelry terms pulled straight from the AliExpress source listing or spec sheet.
5. Use the matched style(s) as the listing's `styles` field value (create-only on `create_draft_listing`, see that field's gotcha above under "Listings — your own shop") rather than defaulting to a guess or leaving it generic.
6. **Rename the product's own gallery images in its `Add Product/Jewelry Products/<Category>/<product>/` staging folder to reflect the matched style/type** (explicit user instruction, 2026-08-19) — e.g. generic filenames like `ChatGPT Image Aug 17, 2026, 03_48_45 AM.png` become keyword-rich, hyphenated names built from the product's core name + matched style, sequentially numbered (e.g. `viking-gothic-wolf-ring-2.png`, `viking-gothic-wolf-ring-3.png`). **Leave the featured/thumbnail image and the size chart image untouched** — they keep their own existing naming convention (the `Featured` marker in the filename, and `Size Chart`/`size chart`) rather than being folded into this style-based renaming. Do this after the style match is confirmed (step 1) so the rename reflects the actual agreed-upon style, not a guess. This is a local file rename only (`Add Product/` staging, not yet an Etsy write) — no confirmation needed, same reasoning as the other local-bookkeeping rules in this file. **This renaming step is never skippable, no exception** (sharpened 2026-08-19 after an audit found 3 of 5 jewelry listings skipped it and uploaded original `ChatGPT Image...`/UUID filenames straight through) — do it for every gallery image, every listing, before calling `upload_listing_image`, not just when it's convenient.
6b. **Hard rule, project-wide, not jewelry-only (explicit user instruction, 2026-08-19): image `alt_text` is derived from the renamed filename, not from the tags array.** This changed the general Image alt text rule in `.claude/skills/_shared/etsy-seo-standards.md` — see that file for the full mechanics (gallery image alt_text = renamed filename with extension stripped and hyphens turned to spaces; featured image alt_text = the product's core/plain name; size chart alt_text = literally `size chart`). Applies to every skill that uploads listing images, not just jewelry. Not retroactive — listings published before 2026-08-19 were not automatically fixed (user declined the retroactive cleanup pass when asked).

This turns jewelry copywriting into a grounded, per-product decision (real photo → real style match → real competitor listings in that style) instead of an "andaza" (guess) carried over from a generic supplier description.

**Claude keeps its own written record of what it observed in the image — a `PRODUCT ANALYSIS` section, separate from the user-filled `SPECIFICATIONS` section (explicit user instruction, 2026-08-19).** Right after filling STYLE MATCH, also fill a `PRODUCT ANALYSIS` section in that product's `product-details.txt` with Claude's own construction/visual findings from the photo — build/construction details actually visible, color(s) actually visible, any size/dimension cues visible or inferable, and any other physical detail worth recording (texture, hardware, closure, motif placement, etc.). This is Claude's own grounded record of what it looked at and concluded, kept separate from the `SPECIFICATIONS` section where the user later pastes the AliExpress spec-sheet text — the two sections exist side by side precisely so a spec-sheet claim that contradicts what's actually visible in the photo (per the photo-verification standing rule above) is easy to catch: compare `PRODUCT ANALYSIS` against `SPECIFICATIONS` before writing the description, and flag any conflict to the user rather than silently picking one.

**The description must clearly define what the product actually is, and must always state its size/dimensions when the product has one (explicit user instruction, 2026-08-19).** Every jewelry listing's description has to describe the actual piece in concrete terms (type, material/finish, construction, style) — not just marketing language that assumes the buyer already knows what it looks like. If the product has any size dimension — ring size or adjustable range, chain/necklace length, bracelet circumference, pendant/charm dimensions, band width, etc. — that figure is mandatory in the description, sourced from `PRODUCT ANALYSIS` (if visually apparent/measurable) and/or `SPECIFICATIONS` (AliExpress-stated exact figures) — never omit it, even if the title/tags already imply a size category. For a one-size/adjustable piece with no fixed numeric size, say so explicitly ("adjustable, fits most") rather than leaving size unaddressed.

**What the AliExpress data is still used for (clarified 2026-08-19): factual specifications, not style keywords.** The AliExpress spec sheet/product-details text the user hands over is still the source for the listing's actual factual specifications — material, dimensions/size, stone type, plating/finish, weight, chain length, care instructions, box/packaging included, and any other concrete attribute of the physical item (subject to the photo-verification rule above — a spec sheet claim that the photo contradicts still doesn't go in). Weave these specifications into the description, written in the shop's own voice per the Copy QA Gate, rather than pasting the source text's phrasing verbatim. What does **not** carry over from AliExpress is the *style/vibe keyword layer* — the broad "boho gothic vintage fairy cottagecore" style-word stuffing suppliers add to rank for every possible buyer search — that part is replaced entirely by the image-match + competitor-listing research in steps 1-4 above.

## Standing rule — every listing description carries a computed DELIVERY TIME FRAME block (explicit user instruction, 2026-07-30)

Every listing's description — on `create_draft_listing`, and any later `update_listing` that touches the description — ends with a `DELIVERY TIME FRAME` block. This is mandatory, not optional, for every skill/flow that writes a description (`etsy-create-listing`, `etsy-new-listing-copywriter`, `etsy-copy-listing`, `etsy-optimize-listing`, `etsy-seasonal-keywords`, or any ad-hoc description edit) — never ship a description without it. Run this as part of Copy QA, not a step that can be skipped because the user didn't ask for it explicitly on a given turn.

The block's boilerplate text is fixed, verbatim every time except the two day-range placeholders:

```
DELIVERY TIME FRAME:
-------------------------------
- Our estimated delivery time (processing time included) is around <US_MIN>-<US_MAX> business days within US, and <INTL_MIN>-<INTL_MAX> business days (about <INTL_WEEKS>) for International shipping. If you have the exact date that you need the items, please let us know.
- For international orders: We will ship from our other warehouses in the EU and Vietnam, depending on the customer's address, to optimize shipping time and cost.
- Wanna add a personal touch for your item? Feel free to contact us, we will be happy to create the one just for you.
***Please note that your order is made uniquely for you, as each item is produced individually after purchase, so we do not accept returns or exchanges.
Please double-check your order before placing it, or feel free to message us if you need help reviewing your selections.
We also cannot offer support or replacements for items that have been used or washed.
Thank you for your understanding!
```

**The `<US_MIN>-<US_MAX>` and `<INTL_MIN>-<INTL_MAX>` numbers are computed per listing, never hardcoded or copied from a previous listing's block.** Add that listing's real processing-profile min/max days (the `readiness_state_id`/processing profile actually attached to this listing) to its real shipping-profile transit days (`get_shop_shipping_profile`'s destinations): use the **US destination's** `min_delivery_days`/`max_delivery_days` for the US line, and the **slowest international destination's** (typically the catch-all/ROW, or EU if ROW isn't set) for the International line — then convert that day range to an approximate week count for the `<INTL_WEEKS>` parenthetical (e.g. 9-19 days → "about 1.5 to 3 weeks"). A different shipping or processing profile means different numbers — recompute every time, don't reuse another listing's figures.

**This block's "we do not accept returns or exchanges" line must match the listing's actual `return_policy_id`.** Before attaching this block, check the return policy being used on the listing: if it accepts returns/exchanges, that directly contradicts this boilerplate — flag the conflict to the user rather than silently shipping a self-contradictory listing (own no-returns policy vs. a return policy that says otherwise). This shop keeps both a returns-accepted and a no-returns `return_policy_id` (see `get_shop_return_policies`) specifically so a made-to-order/no-returns listing can use the matching one.

## Standing rule — jewelry listings use one shared AliExpress shipping profile, and always disclose a production partner (explicit user instruction, 2026-08-19)

For every jewelry listing (from `Add Product/Jewelry Products/`, any account):

**Shipping profile — one shared profile per account, not a fresh one per listing.** All AliExpress-sourced jewelry listings on a given account use a single, shared shipping profile: processing time **3-5 days** (via `get_processing_profiles` — reuse the shop's existing 3-5 day profile, same convention already used elsewhere in this shop, don't create a duplicate), and shipping/transit time **10-15 days, excluding processing** (i.e. the shipping profile's own `min_delivery_days`/`max_delivery_days` = 10-15, separate from the processing days added on top for the buyer-facing estimate). Before creating a new shipping profile for a jewelry listing, check the target account's existing profiles (`get_shop_shipping_profiles`) for one already matching this 10-15-day AliExpress-jewelry shape and reuse it — only create a new one the first time this account lists jewelry.

**Cost split (explicit user instruction, 2026-08-19, supersedes the flat "$5 everywhere" default below for jewelry specifically): the US destination ships FREE (`primary_cost` and `secondary_cost` both $0.00), every other/international destination stays at the standard $5.00/$5.00.** Per the existing AliExpress shipping-profile standing rule above, `secondary_cost` stays at $5.00 on every non-US destination on this profile (bumping `primary_cost` to $5.00 too if it's currently below that) — that general rule still governs every destination except the US leg, which this jewelry-specific override makes free instead.

**Naming (explicit user instruction, 2026-08-19): the shipping profile's own `title` (and every other buyer-facing field on the listing) must never contain a sourcing-platform or business-model name** — no "AliExpress", "1688", "dropshipping", or similar. Name the shared profile something generic like `"Jewelry Shipping"`, never `"AliExpress Jewelry Shipping"`. See the Copy QA Gate's rule 9b in `.claude/skills/_shared/etsy-seo-standards.md` for the full scope of this ban (title/tags/description too) — it does not apply to this project's own internal record-keeping (CLAUDE.md itself, `product-details.txt`, `sources`, `product-registry.json`), only to anything Etsy or a buyer actually sees.

**This feeds directly into the DELIVERY TIME FRAME block above.** Add this profile's processing days (3-5) to its 10-15 day transit to get **13-20 business days**, computed for both the US and International lines — this profile doesn't currently distinguish a slower international destination, unlike this shop's other shipping profiles. If the account's actual profile destinations are later split into different US vs. international transit times, use each destination's real numbers per the general DELIVERY TIME FRAME rule instead of assuming both lines match — recompute rather than keep reusing 13-20 once that changes.

**`who_made` — always `"someone_else"` + a declared production partner, no exception, for every jewelry listing.** This is stricter than the general production-partner standing rule below: skip that rule's "if the account has zero partners, use `i_did`" fallback branch entirely for jewelry — a jewelry listing is always understood to be manufacturing-partner sourced (AliExpress supply chain), never handmade by the seller. Still call `get_shop_production_partners` for the target account first (to get the real partner ID to pass in `production_partner_ids`), but if that account genuinely has zero partners on file, treat it as a hard blocker: stop and tell the user a production partner must be added in Shop Manager (Settings → Production Partners) before this jewelry listing can be created — don't fall back to `i_did` the way a non-jewelry listing on a zero-partner account would.

## Standing rule — every draft/publish syncs its tags to the tags database, and every new draft checks the bank first (STRICT, no exceptions)

This is a hard rule, not something to skip when it seems unnecessary — it applies to `etsy-create-listing`, `etsy-new-listing-copywriter`, `etsy-copy-listing`, `etsy-optimize-listing`, `etsy-seasonal-keywords`, and any ad-hoc tag edit, not just the skills that already mention it.

- **On every draft/publish/tag-update**: the instant a `create_draft_listing` or `update_listing`/tag-changing call succeeds with a final `tags` array, save **every one of those tags** into `data/tags-database.json` — automatically, no confirmation needed (same local-bookkeeping reasoning as the listings-record rule above). Decide the category the same way the shared guide already describes (match by product type, reuse an existing category over creating a near-duplicate one).
- **No duplicate tags in the bank, ever.** Before adding a tag to a category, check (case-insensitive, exact text match) whether it already exists in that category's `tags` object. If it exists, **increment** its `times_seen`/`sample_size`, append a `sources` entry, and update `last_seen` — never write a second entry for the same tag text in the same category. If it's genuinely new to that category, add it fresh.
- **On every new product draft — check the bank BEFORE researching or writing tags.** Look up the tags database by the product's name/type for a matching category. If a match exists, **show the user the saved tags** (with `status`/`times_seen`/`last_updated`) before doing anything else — don't silently skip this check and don't silently decide on the user's behalf whether to reuse them; surface what's already known, then proceed per the shared guide's reuse-vs-fresh-research framing.

Full mechanics (schema, category-matching logic, increment vs. new-entry logic, staleness framing) live in `.claude/skills/_shared/tags-database-guide.md` — this section is the strict, non-negotiable version of that guide's save/reuse workflow; the guide explains *how*, this rule says it is *never optional*.

## Standing rule — every listing carries a `product_id`, and the cross-account product registry stays current (explicit user instruction, 2026-07-29)

Every listing record (`data/listings/<account>/<listing_id>.json`) carries a `product_id` field — a stable slug identifying the underlying product design, independent of any one account's `listing_id`. `data/product-registry.json` is the master index: one entry per `product_id`, listing every account/listing_id that design has been published to. Together these answer "has this product been published to account X yet?" without re-reading every listing file. Full schema and matching rules: `.claude/skills/_shared/product-registry-guide.md`.

- **On every create/clone**: after the listing record is written (per the listings-record rule above), resolve its `product_id` — reuse an existing one from the registry if this is the same design published to a new account, or mint a fresh kebab-case slug if it's a genuinely new product — and stamp it into both the listing record and the registry's matching entry (or a new entry). No confirmation needed, same local-bookkeeping reasoning as the listings-record/tags-database rules above.
- **Before starting a new publish**, check the registry for a matching product first and tell the user which accounts already have it — this is the whole point: catching "I published this on one account, now I need it on the second one" before duplicating research or, worse, the listing itself.
- **Matching is judgment, not exact-title matching** — titles are never cloned verbatim across accounts, so match on `product_template_ref`/`cloned_from` cross-links where present, or distinctive shared phrasing otherwise. When genuinely unsure whether two listings are the same design (e.g. same theme, different garment construction), don't force a merge — keep separate entries and flag both with a `note`, and ask the user to confirm rather than silently guessing.

## Standing rule — every product carries a sourcing record (`sources`), shared across every account it's published to (explicit user instruction, 2026-08-01, STRICT)

**Every listing this system creates must have its supplier source(s) captured — where the actual physical/digital product itself comes from** (a supplier link — AliExpress, Printful, Printify, Merchize, or any other — or plain text if there's no single link, e.g. "in-house DTG print" or "local tailor"). A product can genuinely have **more than one** source (the same design sourced from AliExpress *and* separately available via Printify, say) — `sources` is always an array, never a single value, even when there's only one entry today.

- **Sourcing is a product-level fact, not a per-account/per-listing one.** Per the user's explicit clarification: if the same product design (`product_id`) is later published to a second account, it uses the **same source(s)** already on file — sourcing doesn't reset or need re-asking per account. This is different from shipping/pricing/personalization, which *do* vary per account/listing.
- **Canonical storage: `data/product-registry.json`**, one `sources` array per `product_id` entry (schema and full mechanics in `.claude/skills/_shared/product-registry-guide.md`). **Mirrored copy: every listing record** (`data/listings/<account>/<listing_id>/record.json`, or the flat file for digital listings) under that same `product_id` also carries the identical `sources` array, so a source is answerable straight from one listing's own record — e.g. when an order/receipt names a `listing_id`, resolving its source never requires opening the registry, just that listing's own record — without that lookup depending on the registry file being present or in sync.
- **On every new listing creation: a source is a hard blocker, not just a completeness-gate item to ask about (explicit user instruction, 2026-08-04, STRICT).** Do not call `create_draft_listing` for any listing — physical or digital, any account — until at least one `sources` entry is confirmed. If the user hasn't given a source yet, stop and ask for it (a supplier link, or plain text description) and wait for the answer before proceeding to creation; don't draft first and chase the source afterward, and don't treat "I'll ask later" as acceptable. This applies identically across every sourcing type — there is no type-based exception:
  - **AliExpress/Merchize/Printify/any named supplier** — the source is that supplier link (or the product page URL), same as always.
  - **Custom/in-house products** (`Add Product/Custom/`, no named supplier) — still need an explicit source, even though there's no single supplier link to point to. A plain-text description is a valid source (e.g. "in-house DTG print", "local tailor", "custom embroidery, in-house"), but it must be explicitly given by the user — never silently default to "custom" as if that alone satisfies the requirement, and never leave `sources` empty just because the product has no external supplier.
  - A listing can genuinely have more than one source from the start (see the array shape below) — if the user gives more than one at creation time, capture all of them, not just the first.
- **When the user hands over a source for an existing listing** (a link, or text, given ad hoc — "iska source ye hai", or a batch of listing-wise sources): resolve that listing's `product_id`, then **check the registry for every other account/listing_id under that same `product_id`** — if the product has already been published elsewhere, update the source there too (both the registry entry and every sibling listing's own record), not just the one listing the user happened to name. This is the whole point: one source update should propagate to every account carrying that product, automatically, no separate confirmation needed (local bookkeeping, same reasoning as the other mandatory local-record rules above).
- **Multiple sources, appended not replaced**: when a new source is given for a product that already has one on file, append to the `sources` array (dedupe on exact link/text match) rather than overwriting — a product can accumulate more than one legitimate supply source over time, and past ones stay valid history even after a new one is added.
- **Schema** (both in the registry, per `product_id`, and mirrored per listing record):
  ```json
  "sources": [
    {"type": "link" | "text", "value": "<URL or plain description>", "label": "<short supplier name, e.g. \"AliExpress\", \"Printify\", omit if not obvious>", "added_date": "<ISO date>"}
  ]
  ```
- **Retrieval use case this exists for**: whenever an order/receipt or any other request resolves down to a specific `listing_id`, and the user (or a skill) needs to know where that product actually comes from — look up that listing's own record's `sources` field directly (no need to cross-reference the registry unless the listing record is itself missing/stale, in which case fall back to the registry by `product_id`).

Full schema and matching mechanics for the registry side live in `.claude/skills/_shared/product-registry-guide.md`; the listing-record mirror follows `.claude/skills/_shared/listings-record-guide.md`'s existing sync-on-every-update pattern — this rule is the strict, non-negotiable statement that `sources` must exist and must propagate; those guides carry the field-level detail.

## Standing rule — a deactivated/replaced listing collapses to exactly one current record per product (explicit user instruction, 2026-08-01)

**Only one listing per `product_id` is ever treated as "the" listing going forward — never two live-looking local records for what is really one product's current state.** This came up when Etsy froze a listing (`state: edit`, `"This listing is not publishable because it's frozen."`, no API-side fix — see the `update_listing`/personalization section below for the general "frozen listing" gotcha) and the fix was a brand-new `create_draft_listing` with the same product data but reworded copy. The new listing_id is a different Etsy object, but it is still the *same product* — the local bookkeeping must reflect that, not fork into two parallel histories.

Whenever a locally-tracked listing (one with a `data/listings/<account>/<listing_id>/` folder and a `product_id`) gets deactivated by Etsy — frozen, policy-flagged, manually pulled, or any other way it stops being the live listing — and is republished with changes (whether that republish is an edit to the *same* `listing_id`, or, when that's impossible, a *new* `listing_id`, on the *same* account or a *different* one):

- **Resolve the account and the full new data first** — which account the republished listing actually lives on, and its complete current state (title, tags, description, price, images, video, everything the listings-record schema tracks) — exactly like any other create/update.
- **Update `data/product-registry.json`'s existing entry for that `product_id`** so its `listings` array points at the new `listing_id`/account as the live one. Don't leave the old, now-dead `listing_id` sitting in that array looking like a second valid, currently-published copy of the product — either drop it from the array entirely (once the old listing is actually gone from Etsy) or mark it unmistakably retired/frozen/deleted with a `note` explaining what happened and when, while the array itself reflects only what's genuinely live today.
- **If the old listing is still sitting on Etsy in a dead state (frozen, unpublishable) after the replacement goes live, don't leave it there as silent clutter** — ask the user whether to delete it from Etsy (per the delete-confirmation rule above) so the shop itself also converges on exactly one listing per product, the same way the local records do.
- **Once the old listing is deleted from Etsy**, remove its local `data/listings/<account>/<listing_id>/` folder entirely (images, video, `record.json`) rather than keeping a dangling record for a listing_id that no longer exists — the product-registry's `note` field is where the historical fact ("this product used to be listing X, which got frozen and replaced by listing Y on 2026-08-01") belongs, not a leftover folder.
- **This is local bookkeeping, same reasoning as the listings-record/tags-database/product-registry rules above** — no separate confirmation needed for the record-keeping itself once the underlying Etsy create/update/delete calls have each been confirmed on their own.

The end state for any given product, at any point in time: one `product_id` entry in the registry, pointing at exactly one live `listing_id`/account, with one local record folder — never a trail of stale duplicates.

## Standing rule — shop onboarding builds a "Shop DNA" per account, and a new shop gets a 7-day launch plan (explicit user instruction, 2026-10-07)

Every connected account has `data/shops/<account>/shop-dna.json` — what the shop sells, to whom, in what voice, at what price band, from which suppliers, and what it must never do. Skills read it **first** so they work with the shop's identity instead of guessing. Built by **`etsy-shop-onboarding`**, which **always asks first: is this a new shop or a running shop?**
- **New shop** → asks the short, high-value question set (category/niche, how it sells and is sourced, buyer, price tier, style, shipping origin/speed, shop name, owner facts, never-sell list), writes the setup kit (shop title, announcement, sale message, section names, About story, tagline, FAQ, policies text, logo/banner briefs), applies only the API-writable parts after table confirmation (`update_shop`, `create_shop_section`), and starts the **7-day launch plan** (`data/shops/<account>/launch-plan.json`, playbook in `.claude/skills/_shared/launch-7day-playbook.md` — all setup, 10 listings, QA, publish and a baseline inside 7 days).
- **Running shop** → reads the live shop (Haiku sub-agent for the reads), **infers** the DNA from listings/tags/prices/profiles/reviews, shows it for correction, then saves it.
- About story, logo, banner, team, and returns/cancellations/privacy policies have **no API write** — the skill drafts, the owner pastes. Owner facts are never invented. A missing `shop-dna.json` is a nudge to offer onboarding, never a hard block. Schema and rules: `.claude/skills/_shared/shop-dna-guide.md`.
- When a new account is connected (see "Connecting a new account" step 6), offer onboarding right away.

## Standing rule — rank-first title formula (explicit user instruction, 2026-10-07)

A listing title is never written from the supplier text or from memory. First pull the **top 20 ranking listings** for the buyer's search term (Haiku sub-agent for the read), cut each title at 40 characters, count the lead phrases and structure, show the pattern as a table, and build characters 1-40 from that pattern; the rest of the title adds distinct angles (no repeated words). Patterns are cached in `data/title-patterns.json` and re-checked after 30 days. Applies to every skill that writes a title. Procedure and honest limits (API ordering is an approximation of Etsy's ranking, sample is small): `.claude/skills/_shared/rank-first-title-guide.md`.

## Standing rule — account-level risk is scanned, not just screened at creation (explicit user instruction, 2026-10-07)

## Standing rule — local records are verified against live Etsy, not trusted (explicit user instruction, 2026-10-07)

**`etsy-sync-check`** keeps the record system honest: `node scripts/local-integrity.mjs` (local records ↔ registry ↔ `accounts.json`, no API) and `scripts/sync-diff.mjs` (live listings, fetched by a Haiku sub-agent, vs local records; `--apply` writes live values into records, `--snapshot` appends views/favorites to `data/metrics/<account>.jsonl`). Run after any batch of edits/publishes, at the end of launch week, and weekly with `--snapshot` — those snapshots are the only performance trend this system can get (`getListing` returns cumulative `views`/`num_favorers` for active listings; directional only). Report drift; apply live→local only after the user says yes; a listing that went `active`→`edit` is a risk event (run `etsy-risk-scan`), not something to "fix" by syncing.

## Project layout

- `etsy-mcp-server/` — the MCP server (Node.js/TypeScript) itself: `src/index.ts` is the source, `npm run build` compiles it to `build/index.js` (what `.mcp.json` actually launches), plus `accounts.json`/`.env` (credentials) and `oauth-setup.js`. This folder is server code and credentials only — the local data store below lives at the project root, not inside here.
- `etsy-mcp-server/.env` — default app-level credentials (gitignored). Just `ETSY_API_KEY` / `ETSY_SHARED_SECRET`, required on every request. Used by any account that doesn't carry its own `api_key`/`shared_secret` in `accounts.json` (see below) — i.e. the default app, not necessarily the only one.
- `etsy-mcp-server/accounts.json` — **multi-account store** (gitignored). Shape:
  ```json
  { "default_account": "svgpngkingdom",
    "accounts": {
      "svgpngkingdom": { "shop_id": "52245094", "shop_name": "SVGPNGKINGDOM", "access_token": "...", "refresh_token": "..." },
      "abbas_etsy": { "shop_id": "...", "shop_name": "...", "access_token": "...", "refresh_token": "...", "api_key": "nwn9g575t16qwhg2fmjoiffy", "shared_secret": "lfdixxbl1a" }
    } }
  ```
  Every OAuth-authenticated tool takes an optional `account` argument (falls back to `default_account` when omitted). Access tokens auto-refresh on a 401 and get rewritten here — nothing to do manually. `api_key`/`shared_secret` are **optional per account** — present only when that account was connected through its own separate Etsy Developer App (different keystring/shared secret than `.env`); when absent, the account falls back to the default `.env` credentials. `index.ts`'s `getOauthClient`/`refreshAccessToken` already read this fallback — no code changes needed to add more accounts, whether they share the default app or bring their own.
  - **Account `status` (added 2026-09-02): `"active"` (default when the field is absent) or `"deactivated"`.** Set via the **`set_account_status`** tool (`account`, `status`), not by hand-editing the file. A deactivated account is fully blocked — `getAccount` throws on it, and every code path that resolves a client (`getOauthClient`, `getPublicClient`) checks this *before* trusting a cached client, so an account deactivated mid-session can't keep working through a client made while it was still active. Deactivating the current `default_account` clears `default_account` entirely (forcing an explicit `set_default_account` call afterward) rather than silently leaving every no-`account`-argument call pointed at a dead account. `list_accounts` reports each account's `status`. Currently deactivated: `abbas_etsy`, `itrat_etsy` (2026-09-02, user instruction — kept connected/credentialed but not for active use). To reactivate, call `set_account_status` with `status: "active"`.
- `data/` — **the whole local data store lives at the project root** (moved 2026-07-31 out of `etsy-mcp-server/data/` so it's not buried inside the server subfolder). None of it is read or written by the server code (`src/index.ts` never touches this path) — it's pure Claude-side bookkeeping, read/written directly with the Read/Write/Edit file tools by whichever skill is running. Gitignored in its entirety (one `data/` rule in the root `.gitignore`) — shop-specific runtime state, never shared across installs, and every account's data is kept strictly separate (see the `data/listings/<account>/` bullet below — one folder per connected account, never a shared/merged file, since shipping/pricing/personalization all differ by account even for the "same" product). The four stores inside it:
- `data/tags-database.json` — **accumulated tag research store** (gitignored, like `accounts.json`). Not an Etsy API resource — plain local JSON that skills read/write directly with the Read/Write/Edit file tools. Holds tags saved from past competitor/best-seller research, organized into skill-decided categories (e.g. `boho-wall-decor`) with a `common` vs `unique` classification and a cumulative `times_seen`/`sample_size` count per tag. Full schema and the save/reuse workflow live in `.claude/skills/_shared/tags-database-guide.md`. Research skills (`etsy-keyword-research`, `etsy-optimize-listing`, `etsy-new-listing-copywriter`, `etsy-audit-listing`, `etsy-niche-scanner`) always save tags they surface here automatically — no confirmation needed, it's local bookkeeping, not an Etsy write; create/optimize skills (`etsy-new-listing-copywriter`, `etsy-optimize-listing`) check it first and offer to reuse a matching category instead of researching from scratch.
- `data/products/<Supplier Name> products/<product-slug>.json` — **saved product templates, organized by supplier** (gitignored, like `accounts.json`/`tags-database.json`). One JSON file per product built by `etsy-create-listing` from a source URL (e.g. a Merchize/dropship product page), grouped into a per-supplier subfolder (`Merchize products/`, `Printify products/`, etc. — this shop sources from multiple suppliers, so templates are never mixed into one flat folder): the full copy (title/tags/description), taxonomy, materials/styles, variant structure with per-SKU pricing, the image source list (including the original `source_url`), and a reusable shipping-profile shape, plus a `published_listings` history of every account/listing_id it's already been published to. The point: publishing the *same* product to a *different* (or the same) Etsy account later reuses everything account-agnostic and only redoes the genuinely account-specific parts (shipping/processing profile, the actual `create_draft_listing`/`update_listing_inventory`/image-upload calls — every write still gets its own confirmation, reuse only speeds up research). Full schema and the save/reuse workflow live in `.claude/skills/_shared/product-templates-guide.md`.
- `data/listings/<account>/<listing_id>/` — **as-built, kept-current record of every listing this system has created**, one subfolder per connected account, never shared across accounts (gitignored, like the stores above). Unlike the product-templates store (a reusable *recipe*, opt-in), this one is **mandatory and stays current for the listing's whole life, not just at creation**. **Folder-based for physical listings** (updated 2026-07-31): each listing gets its own `<listing_id>/` folder containing `record.json` plus the listing's own `images/01.jpg, 02.jpg, ...` and `video/video.mp4` — the actual media files, copied in at upload time, not just Etsy CDN references, so the listing survives even if its Etsy account or the original staging folder (`Add Product/AliExpress/`, `Add Product/Merchize/`, `Add Product/Custom/`, etc.) ever disappears. **Digital listings stay on the older flat-file convention** (`data/listings/<account>/<listing_id>.json`, no folder) since Etsy's API exposes no downloadable copy of a digital deliverable to save locally. `etsy-create-listing`/`etsy-new-listing-copywriter` write the record incrementally on creation (right after each successful `create_draft_listing`, `update_listing_inventory`, image/video upload), and **any later successful `update_listing`/`update_listing_inventory`/image call from any skill** (`etsy-optimize-listing` rewriting copy, `etsy-seasonal-keywords` rotating tags, or an ad-hoc edit) must sync the changed fields back into that listing's record too — no user prompt needed for any of this, it's local bookkeeping alongside the confirmed Etsy write. Holds the full field payload, variants, and image list as they currently stand, plus a `product_template_ref` cross-link back to the product template if the listing came from one, and a `product_id` cross-link into the cross-account product registry (see below). Full schema and the sync-on-every-update rule live in `.claude/skills/_shared/listings-record-guide.md`.
- `data/product-registry.json` — **cross-account product tracking index** (gitignored, like the stores above). One entry per `product_id` (a stable slug for one underlying product design), each listing every account/`listing_id` that design has been published to — the fast answer to "has this product reached account X yet" without opening every listing record. Every listing record's `product_id` field cross-links back into this file. Mandatory for every listing, whether or not it also has a product template. Full schema, matching rules, and the update workflow live in `.claude/skills/_shared/product-registry-guide.md`.
- `data/shops/<account>/` — **Shop DNA + launch plan per account** (`shop-dna.json`, `launch-plan.json`); see the onboarding rule above and `.claude/skills/_shared/shop-dna-guide.md`.
- `data/title-patterns.json` — cached rank-first title patterns per product category (re-check after 30 days). `data/metrics/<account>.jsonl` — weekly views/favorites snapshots written by `etsy-sync-check --snapshot`.
- `scripts/` — deterministic helpers, **no API calls**: `local-integrity.mjs` (record/registry/accounts consistency), `sync-diff.mjs` (live-vs-local diff), `risk-prefilter.mjs` + `risk-terms.txt` (brand/IP/AI/sourcing-word scan of records and `Add Product/` staging). Plain Node (>= 18), no dependencies, identical on macOS, Windows and Linux. `setup.mjs`/`setup.sh`/`setup.cmd` are the cross-platform installer + doctor (see Antigravity section and `SETUP.md`). Skills call these first so the model only judges what the scripts surface.
- `Add Product/` — **manual pre-listing staging area** (moved 2026-07-31 into one parent folder, split by sourcing type), one subfolder per product-in-progress (images, a size chart if apparel, a video). Not part of the `data/` store and not gitignored the same way — this is raw working material staged *before* a listing exists, not a record of one that does. Once a listing is created, its own images/video are copied into that listing's `data/listings/<account>/<listing_id>/` folder (per the bullet above) so the listing's local record is self-contained and decoupled from wherever it was originally staged — the staging folder can be reorganized or cleaned up afterward without breaking anything already published. Subfolders, one per sourcing type (or, for jewelry, one dedicated folder regardless of sourcing type — see below):
  - `Add Product/AliExpress/` — AliExpress-sourced dropship products. Includes a `_template/product-details.txt` fill-in-the-blank sourcing brief (account, source URL, variations, pricing, personalization, materials) — see `etsy-create-listing`'s AliExpress intake step.
  - `Add Product/Merchize/` — Merchize-sourced embroidered products (has a Merchize SKU/pricing sheet, e.g. `Embroidered Unisex T-shirt SKU information.xlsx`). Per the standing rule above, a Merchize listing needs that sheet plus markup confirmation before creation.
  - `Add Product/Custom/` — everything else: in-house DTG-print designs, generic print-on-demand (e.g. Gildan blanks) with no Merchize sheet, or any product without a named supplier.
  - `Add Product/Jewelry Products/` — **all jewelry products, regardless of supplier, live here specifically** (explicit user instruction, 2026-08-19), not under `AliExpress/`/`Custom/` even when AliExpress-sourced. Organized **category-wise**: a subfolder per jewelry category (e.g. `Rings/`, `Necklaces/`, `Bracelets/`) — the user creates these as products are added; don't assume a fixed category list. Each product gets its own subfolder inside its category folder (commonly named by its AliExpress product ID, e.g. `3256806165172385/`), holding that product's images plus a `product-details.txt` copied from `_template/product-details.txt` and **filled in by the user** — same "user fills the intake form" convention as `AliExpress/`'s template, not something Claude generates. See `Add Product/Jewelry Products/README.txt` for the full workflow. Two things that differ from the plain `AliExpress/` workflow:
    - The template's **STYLE MATCH section is filled collaboratively, not upfront**: the user leaves it blank, Claude analyzes the featured image and reports which saved aesthetic/style it matches (per the "jewelry listings match the featured image..." standing rule below), then the user adds real Etsy reference listing IDs/URLs in that same style for Claude to research from — never the other way around.
    - **Status tag on publish is a single flat `" - created"` suffix**, not the `AliExpress/` folder's two-stage `[draft]`/`[active]` bracket tags — e.g. `3256806165172385` → `3256806165172385 - created` once the listing is drafted/published. Rename the product's own subfolder (not the category folder) when this happens.
    - Every other standing rule in this file (sourcing/`sources`, the listings-record JSON, the product registry, the tags database, Copy QA Gate, DELIVERY TIME FRAME block, trademark screening, etc.) applies to jewelry listings exactly as documented elsewhere — this folder only changes *where the product stages and how the intake file behaves*, not any downstream write/record-keeping rule.
- `Shoots/` — raw photoshoot images not yet assigned to a specific product (separate from `Add Product/`, which is organized per-product).

### Connecting a new account

When the user gives you an account name plus Etsy keys (keystring + shared secret) to connect, or just an account name if it's meant to reuse the default app:

1. **Always use the remote OAuth flow, never the localhost one** — the localhost flow (`node oauth-setup.js <name>`, no flags) opens a local port-3945 listener that only works if Claude and the user's browser are on the same machine/session; the **remote flow uses the already-configured `aamirali.com/etsy-callback.php` catcher**, which works regardless. Use the two-step split (`--init` then `--complete=`) since Claude runs the commands non-interactively:
   ```
   node oauth-setup.js <account-name> --init                        # if reusing the default .env app
   ETSY_API_KEY=<keystring> ETSY_SHARED_SECRET=<shared_secret> node oauth-setup.js <account-name> --init   # if given separate keys
   ```
   This prints an authorize URL — give it to the user and ask them to open it, log in as that shop's owner, approve, and paste back the `<state> <code>` line the catcher page shows.
2. Before sending the URL, remind the user (once) to confirm `https://aamirali.com/etsy-callback.php` is registered as a Callback URL on that Etsy app's dashboard (alongside the localhost one Etsy apps support multiple registered callback URLs).
3. Once they paste back the line, complete it with the same env vars used in step 1:
   ```
   node oauth-setup.js <account-name> --complete="<pasted state> <pasted code>"
   ```
   This writes `shop_id`/`shop_name`/`access_token`/`refresh_token` into `accounts.json` — and `api_key`/`shared_secret` too, whenever they were passed via env override, so future refreshes automatically use the right app.
4. Confirm the connection works with a cheap read call (e.g. `get_shop` or `get_me` with that `account`) before telling the user it's done.
5. **Register the new account in the "Etsy Order" Google Sheet** (spreadsheet ID `1sKw8DjlHPFxHtlR_0r4JJtWI1KhoSW7EUxXpPMDTEE4`) so it's tracked and shows up in the fulfillment dashboard from day one — explicit user instruction, 2026-08-01. This is local-adjacent bookkeeping, not an Etsy write, so no confirmation needed, same reasoning as the other automatic sheet updates:
   - Append the account's display name (capitalized, e.g. `Newshop`) to the `Index` tab's `Accounts` list (currently `Index!B3:B5` — extend with a new row directly below the last one, e.g. `Index!B6`).
   - Add a matching row to the dashboard table on the `Index` tab (`Index!B12:K15` as of 2026-08-01, extended from `I` to `K` to cover the `Total COGS (USD)`/`Total Profit (approx.)` columns added 2026-08-01 — verify current row numbers with `get_sheet_data` first, since the table grows one row per account) with the same `COUNTUNIQUEIFS`/`SUMIF` formulas as the existing account rows (just swap the account-name cell reference), and update the `TOTAL` row's `SUM()` ranges to include the new row.
   - Full mechanics, formula patterns, and the exact dashboard schema: `.claude/skills/_shared/order-management-sheet-guide.md`.
   - This only registers the account for tracking — it does **not** pull any orders. Pulling that account's actual orders still goes through `etsy-order-sheet-sync` as a separate step (either right away or whenever the user next asks).
6. **Offer shop onboarding** (explicit user instruction, 2026-10-07): once the account is connected and registered, offer `etsy-shop-onboarding` — it asks new-vs-running first, builds the Shop DNA, and (for a new shop) the setup kit and 7-day launch plan.

### Session account context

Once the user tells you which account to work on (by name, or by giving you keys to connect one), **treat that as the active account for the rest of the session** — pass it as the `account` argument on every subsequent tool call without asking again. Only re-confirm if the user names a different account or the request is ambiguous about which shop it targets. Don't make the user repeat "on account X" for every message.
- `etsy-mcp-server/oauth-setup.js` — authorization helper, **one run per account**. **Default to the remote flow, not the localhost one** — see "Connecting a new account" below for the exact steps and why.
- `list_accounts` / `set_default_account` tools — see which accounts are connected and switch the default without re-running OAuth.
- `.mcp.json` — registers three MCP servers: `etsy` (this project's own server), `etsy-docs` (Etsy's hosted, read-only spec-knowledge server at `https://mcp.api.etsycloud.com/mcp` — has no write access, just documentation), and `google-sheets` (`mcp-google-sheets`, run via `uvx --with "mcp<2" mcp-google-sheets@latest` — the `mcp<2` pin is required, an unpinned `uvx` resolves `mcp` SDK 2.0.0 which removed the `mcp.server.fastmcp` module this package imports, failing with `ModuleNotFoundError: No module named 'mcp.server.fastmcp'`; auth is OAuth via `CREDENTIALS_PATH`/`TOKEN_PATH` pointing at `sheets-oauth.json`/`sheets-token.json` in the project root, gitignored, copied from the sibling SEO project's already-authorized Google account). See the "Etsy Order" Google Sheet standing rule above and `.claude/skills/_shared/order-management-sheet-guide.md` for what this server is used for.

## Which tool to call — quick map

The `etsy` MCP server exposes ~100 tools. Full parameter-level detail lives in the tool descriptions themselves, and exact field names for any endpoint can always be looked up live via the **`etsy-docs` MCP's `get_endpoint`** tool (pass the Etsy `operationId`) — don't hand-maintain a duplicate field reference here, it will drift from the real API.

**Array-typed fields are auto-coerced.** Every write tool that goes through the generic dispatcher (`callWriteEndpoint` in `index.ts`) runs `coerceJsonLikeStrings` on the arguments before building the request: any argument that arrives as a *string* shaped like a JSON array/object (e.g. `tags` arriving as the literal text `["a","b"]` instead of a real array — this happened in practice and produced either an opaque `400`/`"Request failed with status code 400"` or, once the array shape did get through, Etsy's own `"contains invalid characters"` on `/tags` from the literal `[`/`"`/`,` characters) gets `JSON.parse`d back into its real type first. This is a permanent server-side fix, not a per-call workaround — no skill needs to special-case array fields because of it. If a future write call still 400s on an array-shaped field, check this function still runs before assuming the field name or value is wrong.

**Public / read-only (no OAuth, any shop or listing):**
`search_listings`, `get_listing_details`, `search_shops`, `get_shop_by_name`, `get_shop_listings`, `get_shop_reviews`, `get_trending_listings` — browsing/market-research on any shop, not just your own. **`get_shop_by_name` bug fixed**: it originally called `GET /application/shops/{shop_name}`, which is actually the numeric-ID `getShop` endpoint — passing a name string there failed with `"Expected int value for 'shop_id' (got string)"`. Etsy has no get-by-exact-name endpoint; the tool now goes through `findShops` (`GET /application/shops?shop_name=...`, the same fuzzy-search endpoint `search_shops` uses) and picks the case-insensitive exact match, returning `{found: false, similar_matches: [...]}` when there isn't one.

**Listings — your own shop (OAuth):**
`get_listings_by_shop`, `find_all_active_listings_by_shop`, `get_listing`, `get_listings_by_ids`, `get_featured_listings_by_shop`, `get_listing_properties`, `get_listing_property` — read.
`create_draft_listing`, `update_listing`, `delete_listing`, `update_listing_property`, `delete_listing_property` — **write, confirm first**. These go through the generic dispatcher (`additionalProperties: true`), so every field `createDraftListing`/`updateListing` accepts (title, description, price, quantity, who_made, when_made, taxonomy_id, shipping_profile_id, return_policy_id, materials, shop_section_id, processing_min/max, tags, styles, item_weight/length/width/height + units, is_supply, is_customizable, should_auto_renew, is_taxable, type, image_ids, state, etc.) already works — pass them as extra arguments, no code changes needed. Exact field list: `etsy-docs`'s `get_endpoint` for `createDraftListing`/`updateListing`. Two field-level gotchas confirmed against the live API (not obvious from field names alone):
  - **`readiness_state_id` is required on `create_draft_listing` for physical listings** (Etsy added this on top of the older `processing_min`/`processing_max` pair) — call `get_processing_profiles` first (same pattern as `get_shop_shipping_profiles`) and pass an existing `readiness_state_id`, or `create_processing_profile` if none fit. Omitting it fails with `"A readiness_state_id is required for physical listings."`.
  - **Fixed server bug: `create_draft_listing` needs the `?legacy=true` query param to accept `readiness_state_id` at all.** Confirmed live: sending a fully valid payload (real `shipping_profile_id`, real `readiness_state_id` from `get_processing_profiles`, a known-good `taxonomy_id`) still failed with an opaque `"Request failed with status code 400"` no matter what — bisected by removing fields one at a time until only `shipping_profile_id`+`readiness_state_id` together triggered it (each alone was fine, or gave the normal clear "required" error). Root cause: `etsy-docs`'s `get_endpoint` for `createDraftListing` documents a `legacy` query param — *"This parameter is needed to enable new parameters and response values related to processing profiles"* — which this server's endpoint path never set, so Etsy silently rejected `readiness_state_id` (a processing-profile field) with no useful error text. Fixed in `index.ts` by hardcoding the endpoint path to `/application/shops/:shop_id/listings?legacy=true` (same pattern as `update_listing_personalization`'s hardcoded query param) — rebuilt, needs a session restart to take effect. If a future opaque 400 on this endpoint reappears after that restart, this specific cause is already ruled out.
  - **`who_made: "someone_else"` (or `"collective"`) requires the shop to have at least one declared Production Partner, or `create_draft_listing` fails with the same opaque `"Request failed with status code 400"`, no useful error text.** Confirmed live by bisection: an otherwise-identical payload (same `shipping_profile_id`, `taxonomy_id`, `readiness_state_id`, `return_policy_id`) succeeded with `who_made: "i_did"` and failed every time with `who_made: "someone_else"`, isolated by changing that one field. `get_shop_production_partners` returned `count: 0` for the shop in question — Etsy requires manufacturing-transparency disclosure (a Production Partner) for any listing not marked handmade by the seller. **There is no API endpoint to create a production partner** (`getShopProductionPartners` is read-only in Etsy's own Open API — confirmed via `etsy-docs`) — it must be added manually through Etsy's Shop Manager (Settings → Production Partners).
  - **Standing rule (user decision, 2026-07-22; sharpened 2026-08-03): `get_shop_production_partners` for the target account is a MANDATORY first check on every physical listing creation, never skippable — this decides `who_made`, it isn't an optional nicety.** For any physical listing sourced from AliExpress, Merchize, China, or any other supplier: call `get_shop_production_partners` for the target account first (read-only, no confirmation needed), every single time, before proposing a `who_made` value to the user.
    - **If it returns one or more partners → ALWAYS `who_made: "someone_else"` + `production_partner_ids: [<that partner's id>]`, no exceptions.** This is not conditional on how the item is actually produced or who's asking — if the account has a declared partner, that account's supplier-sourced listings always disclose it. Confirmed live 2026-08-03: `abbas_etsy` has a partner on file (`production_partner_id: 5735985`, "Manufacturing & Fulfillment Partner", China) — every physical listing created for that account uses `someone_else` + that partner id, full stop. Do not default to `i_did` for an account that has a partner configured, even by habit from another account's convention — check per-account, every time, don't assume yesterday's account's answer carries over.
    - **Only if it returns `count: 0`** — don't stop and ask the user whether to add one, create the listing with `who_made: "i_did"` and move on. This was itrat_etsy's established practice while it had no declared partner (every physical listing created before 2026-08-03 used `who_made: "i_did"`, checked directly in `data/listings/itrat_etsy/*.json`) — it's shop-specific practice tied to the zero-partner state, not a project-wide default, and it stops applying the moment a partner is added (see next bullet).
    - **Correction, 2026-08-03: `itrat_etsy` is no longer a zero-partner account.** A live `get_shop_production_partners` check on 2026-08-03 (while creating listing 4548811706) returned `count: 1` (`production_partner_id: 5739762`, "Manufacturing & Fulfillment Partner", China) — contradicting this file's earlier note that itrat_etsy had none. Every itrat_etsy physical listing created from this point forward uses `who_made: "someone_else"` + `production_partner_ids: [5739762]`, same as abbas_etsy's rule above. This is exactly the "production partner later added to a currently-zero-partner account" case the next bullet already anticipated — don't assume itrat_etsy is still zero-partner just because older listings in `data/listings/itrat_etsy/*.json` show `i_did`; always trust a fresh `get_shop_production_partners` call over this file's history.
    - If a production partner is later added to a currently-zero-partner account, that account switches to `who_made: "someone_else"` + `production_partner_ids` for every future listing from that point on.
  - **No tool exists for `taxonomy_id` lookup** — `getSellerTaxonomyNodes` (`GET /application/seller-taxonomy/nodes`) isn't wired into this MCP server, and there's no other tool that returns the actual taxonomy tree data (`etsy-docs`'s `get_endpoint`/`get_guide` only return documentation, never live data). A direct raw API call bypassing the MCP tools was attempted and blocked by the harness's own credential-safety checks — don't try that route. Until a dedicated tool is added, resolve `taxonomy_id` by proposing the best-inferred category and letting the real `create_draft_listing` call validate it live (Etsy rejects invalid IDs with a clear error) — confirmed working in practice: **`taxonomy_id: 1246` ("Accessories > Keychains & Lanyards")** for a personalized acrylic keychain/name-tag listing, and **`taxonomy_id: 1254` ("Ornaments" / holiday decor)** for a personalized acrylic ornament listing — both accepted on the first attempt, so they're known-good values for those categories going forward.
  - **Standing rule (explicit user instruction, 2026-07-29): `taxonomy_id` is always sourced from real reference listings, never invented from general knowledge.** Whether the reference listings come from the user (pasted listing IDs/URLs in a product brief) or from the assistant's own research (`search_listings`/`get_listings_by_ids` during the copy-research phase), pull the `taxonomy_id` those actual listings use — don't independently guess a plausible-sounding category name and match it to a remembered ID. Concretely: call `get_listings_by_ids` on the reference set, look at which `taxonomy_id` the closest-matching listing(s) actually carry, and use that. When reference listings disagree (this happens — e.g. three near-identical nightgown listings used three different taxonomy_ids: 505, 519, 529), pick whichever reference listing's construction/product type is the closest match to the new listing, not just the most common value, and say which listing and why in the confirmation. Only fall back to a "best-inferred category" guess (the older approach above) when zero reference listings exist at all — and flag clearly that it's an inference, not a research-backed match, when that happens.
  - **Variation property IDs may be portable across taxonomies, not taxonomy-specific.** `update_listing_inventory`'s custom-property slot `property_id: 514` (used as a freeform "Size" property) was accepted on both taxonomy 2844 (Welcome Sign, Home Decor) and taxonomy 1254 (Ornament, Holiday Decor) — same ID, different taxonomies, both worked. This suggests Etsy's small set of custom-property IDs (513/514/515 seen so far) are generic slots usable across most/all taxonomies rather than scoped to one category. Worth trying a known-good ID (514 for a single size-like axis) before assuming a fresh lookup is required — no tool exists for discovering these ahead of time either (same gap as taxonomy_id above), so this is still best-effort-then-validate-live.
  - **`quantity` on `create_draft_listing` is capped at 999**, even though the response/local-record `quantity` field can display a higher summed number later (e.g. 999 × 4 variants = 3996 once `update_listing_inventory` sets real per-SKU quantities). Passing a pre-summed cross-variant total (e.g. `3996`) at creation time fails with an opaque `Request failed with status code 400` — no clear message pointing at the field. Fix: always pass `999` (or the single real per-variant quantity for a no-variant listing) as the create-time `quantity`, then set the actual per-SKU breakdown via `update_listing_inventory` afterward. Confirmed by bisecting a 400 down to this field while cloning a listing across accounts.
  - **The `create_draft_listing` request field is `styles` (plural, string array), not `style`.** Confirmed live 2026-08-03: sending `style: ["Gothic","Fantasy"]` (singular) was silently accepted with no error — the listing was created successfully but with an empty style array, because the generic dispatcher just passes through whatever field name is given and Etsy ignores unrecognized ones rather than rejecting them. The *response* schema names this field `style` (singular), which is what makes the mistake easy to make — always use `styles` on the request regardless of what the response echoes back. Same practical consequence as the next bullet below: since styles is create-only, this can't be fixed after the fact if missed.
  - **`styles` is create-only** — `createDraftListing` accepts a `styles` field, but `updateListing` has no `style`/`styles` field in its request body at all (confirmed via `etsy-docs`), so it silently can't be set after the draft exists. Set it at `create_draft_listing` time or not at all through this API — it isn't fixable with a later `update_listing` call.
  - **`price` is also create-only on `updateListing`** — same shape of gotcha as `styles`, confirmed via `etsy-docs`'s `get_endpoint` for `updateListing`: its request body has no `price` field at all. Calling `update_listing` with a `price` argument doesn't error (the generic dispatcher just sends it, Etsy silently ignores the unknown field) — it returns 200 with the OLD price unchanged, which reads as success unless you re-check the returned `price` value. **After a listing exists, price can only be changed via `update_listing_inventory`** (the Inventory API), even for a listing with no real size/color variants — call `get_listing_inventory` first to see the auto-generated single-product record, then `update_listing_inventory` with that product's `offerings[].price` updated. Always re-fetch (`get_listing`/`get_listing_inventory`) after any price-change call and confirm the number actually moved before reporting success to the user.
  - **Personalization (buyer customization box) no longer goes through `create_draft_listing`/`update_listing` at all.** The old `is_personalizable`/`personalization_is_required`/`personalization_char_count_max`/`personalization_instructions` fields on those two endpoints are marked deprecated by Etsy with a removal date of **April 9, 2026** (confirmed via `etsy-docs`) — for any custom/personalized listing (a name, text, photo, or size the buyer enters at checkout), use the dedicated **`update_listing_personalization`** tool instead. **Its real request body is NOT the flat `is_personalizable`/`personalization_*` shape** — that's what `etsy-docs`'s `get_endpoint` misleadingly shows; the actual body (confirmed via `etsy-docs`'s `get_schema` and the `tutorials/personalization/multiple-and-new-question-type-support-examples` guide, and from hitting `"Error: Missing input parameter: [personalization_questions]"` live) is `personalization_questions`: an array of `{question_text, instructions, question_type ('text_input'|'dropdown'|'unlabeled_upload'|'labeled_upload'), required, max_allowed_characters, max_allowed_files, options: [{label}]}` — this call fully replaces all personalization on the listing, so include every existing question's `question_id` (from `get_listing_personalization`) when adding a new one, or it's deleted. The endpoint also **requires the query param `?supports_multiple_personalization_questions=true`** baked into the tool's path (the generic dispatcher sends POST bodies, not query strings, for extra args — so this had to be hardcoded into the endpoint's path constant in `index.ts`, not passed as a normal argument); omitting it 409s. Read with `get_listing_personalization` (public, no OAuth), remove with `delete_listing_personalization`. This is a separate write call after `create_draft_listing` succeeds — confirm it with the user like any other write.
    - **Correction to an earlier note in this file**: `required: false` on a personalization question is NOT broken — confirmed live on `text_input` and `unlabeled_upload` questions added incrementally (each call including the prior questions' `question_id`s plus one new `required: false` question), all 201'd cleanly. The real, reproducible bug was **`labeled_upload` without an `options` array** — that question type requires one `{label}}` entry per upload slot with `max_allowed_files` matching the label count; for a single generic photo field use `unlabeled_upload` instead (no `options` needed). Separately, a **fresh POST creating 3 brand-new questions at once (no existing `question_id`s at all) failed with an opaque `"Request failed with status code 400"`** with no detail in the response body — the identical 3 questions succeeded when added one at a time instead (first question alone, then re-POST with that question's returned `question_id` plus the next new question, etc.). Root cause unconfirmed (Etsy gave no error detail to diagnose from), but the workaround is reliable: if a multi-question `update_listing_personalization` call on a listing with zero existing questions 400s opaquely, retry by adding questions one at a time rather than all at once.
    - **`instructions` has an undocumented-by-the-tool 120-character hard limit** (only visible in `etsy-docs`'s `tutorials/personalization/multiple-and-new-question-type-support` guide, not in `get_endpoint`'s schema output) — exceeding it fails with the same opaque 400 as the `required: false` case above, no character-count error message. If a personalization write 400s for no obvious field-shape reason, check every question's `instructions` length before anything else. Same guide also documents: `question_text` must be 1-45 chars and start with a letter/number; at most one upload-type question per listing; `max_allowed_files` for `labeled_upload` must be ≥2 (use `unlabeled_upload` instead for a single generic photo, no `options` array needed); `max_allowed_characters` required for `text_input` only; `options` required for `dropdown`/`labeled_upload` only.
    - **Two more opaque-400 gotchas confirmed live (2026-07-18, building a Custom Shape Embroidered Patch listing)**: (1) `unlabeled_upload`'s `max_allowed_files` **cannot be `1`** — same undocumented floor as `labeled_upload`'s "must be ≥2", even though `unlabeled_upload` needs no `options` array at all. A single-photo-upload question still needs `max_allowed_files: 2` or higher (e.g. 5), not 1; there's no way to force "exactly one file" through this field. (2) A **`dropdown` question rejects a non-null `instructions` field** with the same opaque `"Request failed with status code 400"` — Etsy's own guide examples show `dropdown` questions with no `instructions` key at all, and live testing confirmed adding one (even a short, valid-length string) breaks the call; omitting `instructions` entirely on `dropdown` questions fixed it immediately. If a `dropdown` question specifically needs explanatory text for the buyer, put it in the `question_text` itself or the listing description, not `instructions`.
  - **A listing in `state: "edit"` after an Etsy policy/IP takedown can become permanently "frozen" — text fields (title/description/tags/etc.) can still be updated via `update_listing`, but `update_listing` with `state: "active"` fails with `"Error: This listing is not publishable because it's frozen."`, even after the offending content (e.g. a trademarked show title in the copy) has been fixed.** Confirmed live 2026-07-29 on two sibling listings (an "Embroidered Appa Sweatshirt" using "The Last Airbender" in title/description, flagged by Etsy on both itrat_etsy and abbas_etsy). Bisected by calling `update_listing` first with just `title`+`description` (succeeded, state stayed `edit`), then with only `state: "active"` (failed with the frozen error) — confirming the freeze blocks the state transition specifically, not the content edit. **There is no known API-side fix**: this isn't a field-shape or payload bug like the other entries in this section, it's Etsy enforcing the freeze server-side regardless of payload. Fixing the copy is still worth doing (it's the actual violation and needs fixing before Etsy will consider lifting the freeze), but don't tell the user "republished" — a frozen listing needs either an automatic Etsy re-review after enough time, or the seller contacting Etsy Support/Trust & Safety directly through Shop Manager; there's no `unfreeze` endpoint or workaround through this MCP server. If republishing is truly needed sooner, the practical path is creating a brand-new listing (fresh `create_draft_listing`) with the corrected copy rather than waiting on the frozen one.

**Listing variations / inventory (OAuth):** `get_listing_inventory`, `get_listings_inventory_by_ids`, `get_listing_product`, `get_listing_variation_images` — read.
**`get_taxonomy_properties`** (`GET /seller-taxonomy/nodes/:taxonomy_id/properties`, public, no OAuth) — added to the server because no tool previously exposed `getPropertiesByTaxonomyId` at all; call this **before** building any `update_listing_inventory` payload to get real `property_id`/`value_id` pairs for standard properties (e.g. "Size") instead of guessing. In a pinch when this is still uncertain, `get_listing_inventory` on a *competitor's* listing in the same `taxonomy_id` (via `get_listings_by_ids`, cross-shop reads work fine for this) also reveals real `property_id`/`value_id` pairs actually in use — useful cross-check, but `get_taxonomy_properties` is the authoritative source since it returns the *full* possible-values list, not just whichever subset one seller happened to use.
`update_listing_inventory` (per-variation SKU/price/quantity — needs a `products` array; see `getListingInventory`'s response shape for the exact structure), `update_variation_images` (assign images to variation values) — **write, confirm first**. Two more requirements the response shape alone doesn't make obvious:
  - Each `property_values` entry that uses one of taxonomy's freeform **"Custom Property"** slots (no fixed `possible_values` list — check `get_taxonomy_properties`) must include an explicit `property_name` string (e.g. `"Type"`, `"Size"`) alongside `property_id`/`values`, or the call fails with `"Expected string value for 'property_name' (got NULL)"`.
  - **This `property_name` requirement also applies to a *standard* property (e.g. `property_id: 200` "Primary color") whenever it's sent with a freeform value not drawn from its `possible_values` list** — confirmed live: sending `property_id: 200` with `values: ["Beige"]`/`value_ids: []` and no `property_name` failed with the same `"Expected string value for 'property_name' (got NULL)"`, even though the property has a real Etsy-known name. Adding `property_name: "Color"` alongside it fixed it. Etsy's own response afterward echoed back `"property_name": "Primary color"` regardless of what string was sent, so the value sent for a standard property's `property_name` doesn't need to be exact — but it must be present and non-null. Safest rule: always include `property_name` on every `property_values` entry, standard or custom, whenever using freeform `values` (empty `value_ids`).
  - Every entry in each product's `offerings` array needs its own `readiness_state_id` (same value as the listing's, from `get_processing_profiles`) — omitting it fails with `"All offerings need readiness state"`.
  - **Any field that varies per product (price, sku, quantity, readiness_state) must be declared in its matching `*_on_property` array**, not just set differently on each product — confirmed live with `"Error: sku must be consistent across all products"` when 4 products had different `sku` values but `sku_on_property` was omitted. Fix: add the controlling `property_id` to `price_on_property`/`sku_on_property`/`quantity_on_property`/`readiness_state_on_property` for every field that actually differs across the `products` array. **Confirmed live again (2026-08-03) on a large tiered listing** (294/378-SKU custom-text hoodie listings, price varying by a "Style and Size" property, `property_id: 513` — Hoodie S/M/L.../5XL, Sweatshirt sizes, Youth Hoodie sizes, Ready-to-print Film, each its own price tier): a bulk +$15 price update first failed with `"price must be consistent across all products"` (fixed by adding `price_on_property: [513]`), then failed again with `"quantity must be consistent across all products"` on the retry — because quantity *also* varies by that same property in this listing. Both had to be declared together: `price_on_property: [513]` AND `quantity_on_property: [513]`. Lesson: when one `*_on_property` fix clears one error, don't assume the payload is now complete — check whether other fields (quantity, sku, readiness_state) also vary across the same controlling property before resubmitting, or expect another consistency error on the same call.
  - **Standard properties (e.g. "Size", `property_id` from `get_taxonomy_properties` or a competitor's `get_listing_inventory`) accept freeform custom values, not just the pre-listed `possible_values`** — confirmed live: sending `property_id: 513` ("Size" on taxonomy 2869) with `values: ["3 inch"]` and empty `value_ids` succeeded, and Etsy auto-assigned a new `value_id` for it. Don't assume a standard property is a closed enum requiring an exact `possible_values` match — a real, sensible value is usually accepted even if it doesn't appear in the taxonomy's suggested list, though `get_taxonomy_properties`'s list is still the safer first choice when the value already exists there.
  - **Every `offerings` entry needs an explicit `is_enabled: true`, or the call fails with the opaque `"Invalid value (null) for boolean"`.** Confirmed live while cloning a 15-variant hoodie listing (5 sizes × 3 colors): a payload with `quantity`/`price`/`readiness_state_id` set on every offering but no `is_enabled` field failed on both a 15-product batch and a bisected single-product test; adding `is_enabled: true` to every offering fixed it immediately. `is_enabled`/`is_deleted` are documented in `etsy-docs`'s `get_endpoint` only as *response* fields, which makes it easy to assume they're server-assigned defaults — they are not; `is_enabled` must be sent on write. Also include `sku: ""` on each product even when not using real SKUs (matches what Etsy echoes back) — not confirmed as strictly required, but sent alongside the fix and no reason to omit it going forward. Separately, a still-unexplained `"Array contains invalid keys: scale_name"` error occurred when a `property_values` entry included an explicit `"scale_name": null` — omit `scale_name` (and `scale_id` is optional too, only needed if you want to echo it) from write payloads entirely; only `property_id`/`property_name`/`value_ids`/`values` are actually required per `get_endpoint`'s documented request shape.
  - **`update_listing_inventory`'s request body rejects `product_id` and `offering_id` entirely, even though both appear on every `product`/`offering` in `get_listing_inventory`'s response.** Confirmed live (2026-07-30, bumping price on two existing hoodie listings): sending each product with its real `product_id` failed with `"Array contains invalid keys: product_id"`; removing that but keeping each offering's real `offering_id` then failed with `"Array contains invalid keys: offering_id"`. Etsy matches products/offerings to existing ones purely by their `property_values` combination, not by ID — send only `sku`, `offerings` (each with `quantity`/`is_enabled`/`price`/`readiness_state_id`, no `offering_id`), and `property_values` (no `product_id` at the product level). This matches `get_endpoint`'s documented request schema, which never lists `product_id`/`offering_id` as request fields — only as response fields; don't assume response-shaped fields round-trip back into the request.
  - **`price` in the request body is a plain decimal amount in the shop's currency (e.g. `53.49` for $53.49), NOT cents/the `Money.amount` integer.** Confirmed live: passing `5349` (thinking of it as cents, by analogy with the response's `amount`/`divisor` pair) got echoed back as `amount: 534900, divisor: 100` — i.e. **$5349.00**, 100x too high, and briefly went live on a real listing before being caught and corrected. `get_endpoint`'s own doc text says this exactly ("assign a float equal to amount divided by divisor") but it's easy to misread given the response shape uses integer cents — always pass the real dollar-and-cents float (`53.49`, not `5349`), and re-fetch after any price write to confirm the number that landed.

  - **`upload_listing_image` can update `alt_text`/`rank` on an already-uploaded, non-deleted image** — pass its existing `listing_image_id` (omit `image_path`) plus the new `alt_text`. The confirmation is per product (a "yes" for one product is not a standing yes for the next). Flags from `etsy-risk-scan`/`scripts/risk-prefilter.mjs` are advisory input to that one question, never a gate that overrides the user's answer. Never silently draft a branded listing, and never rewrite the branded name into a disguised phrasing unless the user asks for that.
- **This does not revive the trademark-symbol formatting note** — the title-field rule allowing ™/©/® *characters* (regex-wise) in `../_shared/etsy-seo-standards.md` is unrelated to this check and stays as-is; this rule is about franchise/brand *names*, not the punctuation marks.

## Deploying to Google Antigravity

**Update 2026-10-07 — Antigravity optimization and cross-platform setup:** every skill, standing rule and script in this project works identically in Claude and Antigravity, on macOS, Windows and Linux. `AGENTS.md` and `GEMINI.md` (project root) and `.agent/rules/00-etsy-project.md` (always-on rule) tell Antigravity to read this file first and translate Claude-specific wording (Haiku sub-agents, `AskUserQuestion`, the Skill tool) into its own tools. **Setup is one cross-platform Node script, `scripts/setup.mjs`** (launchers: `scripts/setup.sh` on macOS/Linux, `scripts\setup.cmd` on Windows): it asks which OS and which AI tool (Claude / Antigravity / both), rebuilds `node_modules` if it was copied from another OS, builds the server, writes the MCP config for *this* machine (project `.mcp.json` for Claude; the global `~/.gemini/antigravity/mcp_config.json` for Antigravity — merged, with a `.bak`, other tools' entries untouched, no secrets written because the server reads `etsy-mcp-server/.env` itself), and smoke-tests the server. `node scripts/setup.mjs --check` is a read-only doctor. The `etsy-setup` skill drives the same flow conversationally. Full human guide: `SETUP.md`. Keep `.agent/skills/` in sync after any skill edit (`rsync -a --delete .claude/skills/ .agent/skills/`, Windows: `robocopy .claude\skills .agent\skills /MIR`) and confirm `diff -rq .claude/skills .agent/skills` is empty before committing. `.gitattributes` pins LF line endings so Windows↔macOS copies stop producing whole-file diffs.

This project also runs on Google Antigravity, not just Claude Code. Two independent things are set up for it — they don't share storage, so both matter:

1. **Skills** — `.agent/skills/` at the project root is a full copy of `.claude/skills/` (identical `SKILL.md` format; Antigravity just reads a different folder name). It's part of the project folder, so copying/cloning the whole project carries it over automatically — nothing to redo. Keep it in sync with `.claude/skills/` any time a skill changes (re-copy the folder, or symlink).
2. **MCP server registration** — Antigravity has a known bug where project-local MCP config (`.agent/mcp_config.json`, `.antigravitycli/mcp_config.json`) is silently discovered but ignored; only the **global, per-machine** config actually spawns servers: `~/.gemini/antigravity/mcp_config.json` (Settings → Customizations → Open MCP Config in the Antigravity UI edits this same file). This file lives **outside** the project folder, so it is *not* carried over when the project is copied/cloned — every machine that runs Antigravity against this project needs the `etsy` and `etsy-docs` entries added there by hand:
   ```json
   "etsy": {
     "type": "stdio",
     "command": "node",
     "args": ["<absolute-path-to>/etsy-mcp-server/build/index.js"],
     "env": { "ETSY_API_KEY": "...", "ETSY_SHARED_SECRET": "..." }
   },
   "etsy-docs": { "type": "http", "url": "https://mcp.api.etsycloud.com/mcp" }
   ```
   (Entry shape uses `"type"`, not `$typeName` — verified against this machine's actual working config; some blog posts describe an older/different schema.) After editing, restart Antigravity (or reopen the project) for the new server to load.

## Handing this project to someone else

Someone getting a copy of this project for **their own** Etsy shop (not svgpngkingdom) needs to:

1. **Copy the whole project folder**, including `.claude/skills/` and `.agent/skills/` — the skill playbooks are shop-agnostic and work unchanged for any shop.
2. **Get their own Etsy Developer app** ([etsy.com/developers/register](https://www.etsy.com/developers/register)) for their own `ETSY_API_KEY` / `ETSY_SHARED_SECRET`.
3. **Build the server**: `cd etsy-mcp-server && npm install && npm run build`.
4. **Set their own credentials**: copy `etsy-mcp-server/.env.example` → `.env`, fill in their key/secret.
5. **Connect their shop**: `node oauth-setup.js <their-shop-name>` — opens a browser, writes their own `accounts.json`. This is what makes every tool (`get_shop`, `update_listing`, etc.) operate on *their* shop instead of svgpngkingdom.
6. **Wire up their AI tool**:
   - *Claude Code*: `.mcp.json` itself is gitignored (it holds this machine's real API key/secret) — copy the committed `.mcp.json.example` to `.mcp.json` and fill in your own path/credentials (or delete the `env` block entirely — the server already falls back to reading its own `.env` file if the host doesn't inject these vars).
   - *Antigravity*: add the same `etsy`/`etsy-docs` entries to **their own** `~/.gemini/antigravity/mcp_config.json` per the section above — this is per-machine and can't be skipped by copying the project.

Nothing inside the skills needs editing — they call tools by name, not by a hardcoded shop ID, so once steps 1–6 are done, every skill (`etsy-audit-account`, `etsy-optimize-listing`, etc.) works against the new shop unchanged.

## Rate limits

Per API key: **5 requests/second, 5,000/day**. Be careful with loops over many listings/orders — batch where a tool supports it (e.g. `get_listings_by_ids`) instead of one call per item.

## Model usage — Haiku for research/reads, Sonnet for planning/writing (STRICT, no exceptions)

**This is a hard, non-negotiable rule, not a default or a suggestion.** Whenever work is delegated to a subagent — the `Agent` tool, or a `Workflow` script's `agent()` calls — the model choice is dictated strictly by task type:

- **Reading = always Haiku.** Any research / reading / data-gathering step — competitor `search_listings` sweeps, reading a large saved tool-result file, summarizing a listing's inventory/variation structure, pulling and aggregating live API data, scanning multiple files for a fact — **must** use the **Haiku** model (`model: "haiku"` on the `Agent` tool; `opts.model: "claude-haiku-4-5-20251001"` inside a `Workflow` script's `agent()` call). No exceptions for "this read is important" or "this file is small" — task type alone decides, not size or perceived importance. This work is mechanical extraction/aggregation, not judgment, and Haiku handles it well at a fraction of the cost and latency.
- **Writing = always Sonnet.** Any planning, synthesis, or writing step — drafting title/tags/description, deciding how to fix something, running the Copy QA Gate, writing this file or a skill file, any step that requires judgment rather than extraction — **must** stay on the main session model (Sonnet, or whatever the user is running). Never delegate this down to Haiku, ever, for any reason.

Do not blend the two in one subagent call ("read this and also decide X") — split into a Haiku read step and a Sonnet judgment step instead, even if it costs an extra round trip.

This applies retroactively to every skill's workflow, not just newly written ones: `etsy-audit-listing`, `etsy-audit-listings`, `etsy-competitor-research`, `etsy-keyword-research`, `etsy-optimize-listing`, `etsy-new-listing-copywriter`, `etsy-create-listing`, `etsy-copy-listing`, `etsy-niche-scanner`, and any other skill that delegates a research/aggregation step to a subagent should pass `model: "haiku"` on that call. If a skill's workflow text doesn't yet say this explicitly, follow this rule anyway — it overrides an unstated default, not just a documented one.
